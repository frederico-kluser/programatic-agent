Modo dev do huu

O que o huu dev é, o que ele faz sozinho, o que ele deliberadamente não faz — e onde ele costuma parar.

huu v5.3.0 30/07/2026 conferido no código
Antes de rodar, três coisas que mexem no seu repo.
  1. Ele faz merge no seu branch atual. A cada época o huu faz merge --no-ff do branch de integração no branch em que você está. Não é um sandbox que você inspeciona depois.
  2. Sua árvore precisa estar limpa. Qualquer coisa não commitada que não seja do huu faz a sessão recusar na hora (dirty-tree).
  3. Autonomia é o padrão. Um huu dev "objetivo" puro planeja e executa tudo até o teto sem perguntar nada. O portão humano é opt-in: --approve-each.

Em uma frase

No huu normal, você escreve o método (o pipeline) e os agentes executam. No modo dev, você escreve só o objetivo — e um planejador LLM escreve o método em tempo de execução, do zero, a cada época.

É o único fluxo do huu cujo grafo de passos nasce durante o run. Todo o resto do huu roda um pipeline.json que um humano escreveu antes.

O loop

Uma época é uma volta completa. O modo dev repete épocas até acabar:

planejar → (aprovar) → rodar → aterrissar no seu branch → replanejar
    ↑                                                          │
    └──────────────────────────────────────────────────────────┘
       até: o planejador dizer "objetivo concluído"
            ou bater o teto de épocas (padrão 3 no CLI)
            ou algo quebrar

Dentro de uma época, o trabalho se abre em leque:

Frentes

O planejador quebra o objetivo em até 4 frentes paralelas (ex.: api, cli, tests). Frentes independentes rodam ao mesmo tempo.

Enxame

Cada frente faz um recon, escreve uma spec markdown por tarefa, e aí dispara um agente por tarefa, cada um na sua git worktree isolada.

Merge

Antes de entrar, o trabalho de cada tarefa passa por um crítico. Depois os branches são mergeados em ordem determinística, e a época aterrissa no seu branch.

Para que serve — e para que não serve

Faz sentido
  • Trabalho que se divide bem por arquivo: migração mecânica, refactor amplo, cobertura de testes.
  • Objetivo com critério de pronto verificável por comando (compila, testa, lint passa).
  • Repo que já tem skills / catalog.md — o planejador cego depende disso.
  • Quando você vai ler o diff no fim. Sempre.
Não faz
  • Objetivo vago (“melhorar o código”). Sem critério mecânico, o juiz vira carimbo.
  • Mudança que concentra num arquivo só — o paralelismo não tem onde acontecer e você paga o overhead à toa.
  • Design novo, decisão de arquitetura, escolha de biblioteca. Isso é humano.
  • Repo com árvore suja ou sem remote/branch em que dê para mergear.

A tensão com o MANIFESTO, dita em voz alta

O MANIFESTO do huu vende “zero planner LLM em runtime” como diferencial e diz que o huu não é ferramenta para desenvolver features novas. O modo dev contraria os dois. O que sobrevive: o humano assina o objetivo (verbatim, ninguém reescreve), a forma da época é do huu e fixa, o modelo escreve conteúdo e nunca estrutura, e todo caminho termina num juiz. O que piora: o merge passa a ser filtrado por um crítico LLM cujo critério é prosa que outro LLM escreveu.

Os três comandos que cobrem 90%

# 1. Autônomo — O PADRÃO. Planeja e roda até o teto de épocas, sem perguntar nada.
huu dev "migrar o parser para streaming sem quebrar a API pública" \
    --model=anthropic/claude-sonnet-4

# 2. Com portão humano: mostra o plano de cada época e espera você confirmar.
huu dev "extrair o cliente HTTP para um pacote próprio" \
    --model=anthropic/claude-sonnet-4 --approve-each --epochs=2

# 3. Ensaio sem LLM: compila o grafo, roda as ondas, faz os merges. Custo zero.
huu dev "qualquer coisa" --stub --epochs=1
--autonomous existe só para você declarar o padrão em voz alta. Não muda nada, e passá-la junto com --approve-each é recusado.

Pela interface web

Um switch no topo separa as duas formas de começar trabalho — e cada metade é uma rota de verdade, então dá para favoritar: 

┌──────────────────────────┬──────────────────────────┐
│ ≡ Pipelines              │ </> Development          │
│   Você já tem o método   │   Você tem um objetivo   │
│   (rota /)               │   (rota /dev)            │
└──────────────────────────┴──────────────────────────┘
  • Goal — o único campo que o run subscreve. O botão de microfone dita: o navegador grava, re-codifica em WAV mono 16 kHz e manda transcrever. Custa cerca de US$ 0,00007 por clipe de quatro segundos, e o texto é anexado ao que já estiver escrito.
  • Project — seleção única: uma sessão de dev termina num merge no branch de um repo.
  • Approval — autônomo vem pré-selecionado, igual ao CLI.
  • Sem teto de épocas. A sessão web roda até o planejador declarar concluído ou você abortar. O CLI mantém --epochs=3 porque um run headless pode estar desacompanhado e não tem botão de Abort.

Enquanto uma sessão roda, a metade Development ganha um ponto pulsante verde — âmbar quando um plano está travado esperando a sua aprovação.

Fase 0 — o portão de conhecimento

Antes de qualquer coisa, o huu sonda o repositório procurando uma superfície de roteamento de skills, nesta ordem:

  1. .agents/skills/catalog.md existe → presente
  2. senão, um .agents/skills/*/SKILL.md que seja roteador (frontmatter type: router, ou os nomes project-router / project-knowledge)
  3. senão, o mesmo sob .claude/skills/

Skills sem superfície de roteamento não contam como “presente” — o planejador não teria por onde entrar nelas. Se estiver ausente, o huu roda o pipeline embutido huu Knowledge System em modo MAX (um agente por tarefa enfileirada até o teto duro, com o guarda de memória como único freio) e aterrissa esse trabalho antes de começar.

Uma época são DUAS runs, não uma

O plano só pode existir depois que o conhecimento chega. Então cada época se parte em três fases: 

A. CONHECIMENTO   run #1 — um pipeline FIXO, sobre o qual nenhum modelo opina
   ① o orquestrador cego declara as LACUNAS de que precisa
   ② o huu, em TypeScript, escreve um .md real por lacuna e COMMITA
   ③ K0 prepara · K1 responde (fan-out) · K2 consolida → digest.md (≤ 6000 chars)

B. PLANO          nenhuma run — lê objetivo + digest + histórico + evidência
                  → compila o pipeline da época → portão → grava pipeline.json

C. EXECUÇÃO       run #2 — o pipeline planejado, com o laço de crítica por tarefa
                  → aterrissa → coleta evidência → replaneja
Zero lacunas ⇒ a fase A é pulada inteira e a época volta a ser uma run só. É o que mantém um --stub em uma run por época.

O planejador é cego — de propósito

Ele não lê arquivo nenhum. Não tem ferramentas, não recebe digest do repositório, não faz grep. A única coisa que ele aprende sobre o seu código é o digest.md que agentes escreveram, com citações de caminhos reais.

Isso não é “planejar sem olhar o repositório”: a fase de conhecimento é o retrieval, só que delegada. Dois mecanismos mantêm a cegueira sem congelar a qualidade:

  • Lacunas de base (época 1): stack e pontos de entrada, comandos de build/teste, onde o objetivo aterrissa, superfície de convenções. É o piso de fundação.
  • Entregue × planejado (época 2 em diante): substitui as lacunas de base por uma pergunta que manda um agente comparar o que a última época prometeu com o que ela realmente entregou.

No schema do briefing, unknowns é obrigatório enquanto facts e sources têm default vazio. A assimetria é intencional: um agente sem lugar para dizer “não consegui verificar isso” escreve enchimento confiante — e um único fato plausível-mas-errado degrada o leitor mais do que uma lacuna honesta.

O que a época vira, compilada

0. Recon do objetivo                          (raiz)
├─ 1a. <frente> — recon        (produz <frente>/tasks.json + uma spec por tarefa)
│  └─ 1b. <frente> — implementar    (fan-out: um agente por spec)
│     └─ 1c. <frente> — verificar  (juiz: approved ↦ segue, rework ↦ volta pro 1b)
├─ 2a/2b/2c …                                  (frentes rodam em ondas PARALELAS)
├─ N+1. Consolidar época      (depende de todos os juízes)
├─ N+2. Portão de qualidade   (juiz: approved ↦ selo, rework ↦ consolidação)
└─ N+3. Selar época

Esse formato é do huu, fixo. O schema do plano não carrega steps, nem dependsOn, nem caminho de arquivo: o modelo é estruturalmente incapaz de emitir um grafo. Ele preenche conteúdo em um molde. E o pipeline compilado ainda passa pelo PipelineSchema de produção + validateTopology antes de rodar — falha ali é bug do huu, não plano ruim.

O quadro-negro (.huu/dev/)

.huu/dev/
  goal.md                    ← o huu escreve, ninguém reescreve
  state.json                 ← o huu escreve (huu-devstate-v2)
  journal.md                 ← agentes acrescentam (append-only)
  <sessionId>/               ← namespace por sessão
    epoch-<N>/
      atlas.md               ← mapa do código, do recon global
      pipeline.json          ← o grafo compilado, auditável e re-executável
      findings/              ← um shard JSON POR ESCRITOR, nunca um arquivo só
      report.md              ← relatório da consolidação
      knowledge/             ← gaps/ · briefs/ · digest.md
      <frente>/
        tasks.json           ← lista huu-memory-v1
        T-001.md …           ← uma spec por tarefa

Duas decisões aqui que parecem detalhe e não são:

  • As specs são arquivos reais, commitados antes da run. O resolvedor derruba qualquer caminho que não exista no worktree de integração — e quando uma lista não-vazia resolve para zero, ele lança erro e mata a run. Efeito colateral bom: o plano fica versionado e auditável.
  • O namespace por sessão não é cosmético. Sem ele, o epoch-1/api/tasks.json commitado por uma sessão anterior é um alvo válido para o fan-out da sessão de agora — e ids de frente são semânticos (api, cli, tests), então a colisão era provável, não exótica.

O laço gerador → crítico

Antes de o branch de uma tarefa ficar elegível ao merge, um crítico lê o diff. O que importa saber:

O que bloqueia Achados de severidade blocker ou major (o padrão). O texto do veredito do crítico é registrado, mas não decide nada — a convergência é mecânica, por severidade.
Quantas rodadas No máximo 2. Estourou o teto com bloqueio ainda aberto ⇒ waive, registra, e o trabalho mergeia.
Se o crítico falhar Estourar, dar timeout, ser abandonado ou devolver algo improcessável ⇒ zero bloqueio, o trabalho mergeia. Toda falha é forward-default.
Por que assim Reprovar o card faria o merge do estágio descartar o branch, transformando “90% certo com um achado major” em nada.

Achados waived não somem: viajam na evidência da época até o próximo planejador. E o crítico roda cross-family (Kimi contra workers DeepSeek) porque “o mesmo modelo barato como autor E revisor” é a suposição mais frágil do desenho.

Limites duros

Nada aqui é bug ou “a fazer”. São escolhas de desenho com custo conhecido — e o custo está escrito.

Essa é a perda. A barreira determinística de merge era o ponto do huu; o modo dev põe a opinião de um LLM na frente dela. O crítico bloqueia por severidade, tendo ou não respaldado o achado com um comando que de fato falhou.

O custo, medido por terceiros: o modo de falha de um crítico LLM é bloquear código correto — de 22,5% a 91,9% de rejeição falsa em 5 modelos × 3 benchmarks, sendo 87,2% disso alucinação semântica, não implicância de estilo. O único remédio que alguém mediu é exigir que o achado seja executável antes de poder bloquear. O huu não exige isso — ele conta: todo achado bloqueante vira “provado” ou “não-provado” no card, para essa escolha poder ser revista com número deste projeto. Trocar para bloqueio proof-gated é uma linha em blockOn.

Uma época é uma barreira: todas as frentes mergeiam antes de qualquer replanejamento. Frentes em profundidades independentes exigiriam abandonar o merge determinístico por estágio, que é a espinha do módulo de git.

É o que cabe no teto de 20 passos do pipeline compilado. O limite é imposto pelo compilador — um modelo que devolva mais frentes do que o pedido simplesmente tem o excedente cortado.

O juiz é uma válvula anti-laço: existe para a época não girar para sempre. Como todo caminho de falha é forward-default, um juiz que quebra aprova em silêncio. Dê um modelo capaz ao juiz e leia o diff você mesmo.

Um card revisado leva até timeout × (1 + rodadas) de relógio, e cada revisão em voo segura um slot do pool — o worker fica não-preemptível enquanto o crítico lê a worktree.

O grafo compila, as ondas escalonam, os merges acontecem — mas o backend stub não escreve arquivo. Então o fan-out resolve para zero tarefas e o laço de crítica nunca roda. É um teste de fiação, não de trabalho. Já houve correção que embarcou completamente inexercitada por causa disso.

A época aterrissa com merge --no-ff no seu branch; desfazer é git na sua mão. E um state.json de formato antigo não é migrado: ele degrada para “sem retomada”, em silêncio e sem código de migração.

O que ele se recusa a fazer

Coisas que o modo dev bloqueia por desenho — não são falhas:

RecusaPor quê
O planejador não pode emitir um grafo O schema do plano não tem steps, dependsOn nem caminho de arquivo. Ele escreve conteúdo, o huu escreve estrutura.
Nenhum agente reescreve o objetivo Entra verbatim em goal.md. O planejador decompõe; nunca amplia, reduz ou reinterpreta.
Duas tarefas não podem possuir o mesmo arquivo Antes de compilar, o huu confere a partição de escrita das specs. Sobreposição para a época — não é aviso.
“Objetivo concluído” na época 1 é recusado Declarar pronto sem nenhuma época executada não tem corroboração. O huu registra o aviso e planeja mesmo assim.
--approve-each sem terminal interativo Encerra sem rodar a época, em vez de travar esperando um enter que nunca vem.
Modelo desconhecido não entra Um preflight valida os ids nos papéis executados antes de criar worktree — recusa limpa em vez de estourar dentro do primeiro agente.
Detalhe fácil de confundir: existem duas mecânicas de write-set. A partição (antes da run, sobre as specs) para a época se duas tarefas reivindicam o mesmo arquivo. Já as violações (depois da run, sobre o que foi realmente commitado fora do declarado) são só instrumentação: contam e viajam na evidência, mas não bloqueiam nada.

Sete papéis, cada um com seu modelo

O modo dev roteia por papel, não por run. Papel deixado em branco omite o campo no passo emitido, então a configuração global do app segue sendo a única autoridade. Sem roteamento nenhum, o pipeline compilado é byte a byte igual ao de antes.

PapelO que faz
plannerO líder cego. Escreve as frentes da época.
reconMapeia o código e escreve as specs de tarefa.
workerO enxame — quem de fato escreve código.
criticLê o diff antes do merge, na worktree do worker.
reporterProsa mecânica sobre um diff (consolidação).
judgeRoda depois do merge, no worktree de integração, e roteia o passo.
integrationTrabalho no worktree de integração.
critic e judge são papéis distintos de propósito. O crítico decide se o branch entra; o juiz roda depois do merge e decide para onde o pipeline vai. Como os caminhos de falha do juiz são forward-default, um juiz fraco aprova em silêncio — por isso ele fica no modelo forte em todos os presets.

Todo preset menos uniform exige o provedor openrouter

Um crítico de outra família precisa de um endpoint que sirva mais de um fabricante, e o OpenRouter é o único que o huu fala — por isso hetero, thrifty e monoculture mandam o planner (e quase sempre o critic) para ids que só openrouter.ai serve, e o roster manda três papéis. Como AppConfig.provider é um provedor para a sessão inteira, pedir qualquer um deles em --provider=deepseek é recusado na borda pelo preflight de modelo, nomeando papel e id — antes de existir worktree, branch ou commit. Na tela /dev os presets que o provedor selecionado não roda aparecem desabilitados, e o formulário abre no melhor preset que ele roda (numa máquina só com chave DeepSeek, uniform).

monoculture não é recomendação. Ele existe justamente para permitir o A/B contra o crítico cross-family — é a configuração que a evidência aponta como a suposição mais frágil do desenho (mesmo modelo como autor e revisor).

z-ai/glm-5.2 só pode ser o planner

Esse id não existe no registro do backend de execução — pedir por ele em qualquer outro papel estoura. O planejador escapa porque ele nunca toca o registro: é o único papel que roda por outro caminho. Por isso o preflight verifica os seis papéis executados e exclui planner no nível do tipo — um preflight que o checasse recusaria o modo dev no seu próprio preset padrão.

Sobre o custo — a conta lida ao contrário

Dividir papéis entre modelos não é economia, e não é vendido como tal. Um fan-out de agentes custa 3–10× os tokens de um agente único, enquanto a diferença de preço entre o líder e os workers é de cerca de 2×. Rotear trabalho para o modelo barato não paga esse multiplicador.

A justificativa real é outra:

  • Isolamento de contexto — cada agente vê só a sua tarefa.
  • Paralelismo — relógio de parede, não tokens.
  • Segunda opinião de outro fornecedor, no caso do crítico.

O custo por época (das duas runs) é medido e viaja na evidência, junto com quantos achados bloquearam com prova, quantos sem, e quantas tarefas foram waived no teto de rodadas. Esses contadores existem para serem medidos — nenhum deles é um portão, e transformar um deles em portão silenciosamente é justamente o que não se deve fazer.

Toda saída tem exatamente um motivo

O CLI imprime um único JSON no stdout com o campo stoppedBecause, as épocas e os commits. São doze motivos possíveis:

Motivo Significa Sai 0?
goal-complete O planejador provou que o objetivo já está satisfeito.
max-epochs Bateu o teto de épocas com tudo aterrissado.
plan-rejected Você recusou um plano no portão.
dirty-tree Havia trabalho não commitado que não é do huu. Recusa antes de começar, com a lista de arquivos.
empty-plan O planejador não deu frentes nem declarou conclusão.
planner-failed O modelo não produziu plano válido — ou duas specs reivindicaram o mesmo arquivo.
run-failed A época terminou com erro.
landing-failed O merge da época conflitou. O huu roda merge --abort antes, então sua árvore volta limpa.
bootstrap-failed O bootstrap de conhecimento não completou.
knowledge-failed A fase de conhecimento (run #1) não completou.
model-preflight-failed Algum papel recebeu um id de modelo que não existe no registro.
aborted Você abortou a sessão.

Os três que mais aparecem

dirty-tree — árvore suja

A sessão precisa mergear no seu branch a cada época; começar com trabalho solto significaria morrer na primeira aterrissagem. Ele recusa na hora, o que é melhor. 

git status --porcelain     # veja o que está solto
git stash                  # ou commite
huu dev "..." --model=...

landing-failed — o merge da época conflitou

Parada real da sessão. O merge --abort já rodou, então a árvore está limpa — mas o trabalho da época ficou no branch huu/<runId>/integration. Ele não se perde: resolva o merge na mão, ou rode a próxima sessão com --land-orphans. O huu detecta branches de integração que o seu HEAD nunca absorveu — trabalho genuinamente perdido que o git status não mostra — e nunca bloqueia por causa disso: sem resposta, ele avisa, nomeia o branch e segue.

planner-failed por partição de escrita

Duas specs de tarefa declararam possuir o mesmo arquivo. Como tarefas paralelas viram merges sequenciais, isso conflitaria em todo branch depois do primeiro. A mensagem de erro nomeia o caminho disputado e as specs que o reivindicam — dá para abrir os .md em .huu/dev/<sessionId>/epoch-<N>/ e ver o plano que gerou aquilo.

Ficou parado, o que olhar

  • Época rodou e não fez nada — provavelmente o fan-out resolveu para zero tarefas. Confira se as specs existem e foram commitadas em epoch-<N>/<frente>/. Se você está de --stub, é o esperado: o stub não escreve arquivo.
  • Card travado revisando — cada revisão em voo segura um slot do pool, e o worker fica não-preemptível enquanto o crítico lê a worktree. Até timeout × 3 é comportamento normal.
  • Plano genérico demais — leia o knowledge/digest.md da época. O planejador é cego: se o digest está vago, o plano tem que sair vago. Um repo sem skills roteáveis costuma ser a causa.
  • Achados vagos do crítico — o padrão contra o qual ele julga é o atlas.md da época. Atlas vago produz achado vago.
  • Não retomou a sessão — a retomada só é oferecida quando o objetivo bate exatamente e a sessão anterior não reportou conclusão. E o teto de épocas conta de onde a sessão começa: um --epochs=3 retomado significa três épocas a mais.
