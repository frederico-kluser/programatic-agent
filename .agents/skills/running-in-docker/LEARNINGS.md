- [2026-07-02][source:user][task:kernel-memory-ceilings][probation] Kernel ceilings (ROADMAP Fase 2.1) landed in BOTH runtimes; four non-obvious facts: (1) the container previously ran UNLIMITED (`buildDockerArgv` had zero resource flags) — it could take 100% of host RAM; now `buildMemoryLimitArgs()` emits `--memory = host total − osReserveBytes()` (→ cgroup memory.max), `--memory-swap = memory + HUU_SWAP_MAX_MB` (allowance ON TOP of memory, docker semantics: memory-swap is the SUM), `--pids-limit 8192`; escapes `HUU_DOCKER_MEMORY_MB` / `HUU_NO_MEM_LIMIT=1`. (2) the operations.md claim that a negative `HUU_OOM_SCORE_ADJ` "takes effect as root inside the container" was WRONG — the container runs `--user <uid>:<gid>` (non-root), so writing a NEGATIVE adj no-ops there exactly like natively (needs CAP_SYS_RESOURCE). The effective lever is the opposite direction: `oom-child-watcher.ts` sweeps /proc every 2 s and RAISES huu's descendants (agent tool children) to +500 — raising needs no privilege (empirically pinned by a real-/proc test) — so kernel OOM kills a vitest worker (→ task retry), not the orchestrator/desktop. (3) native Linux self-wrap: `cgroup-self-wrap.ts` re-execs into `systemd-run --user --scope` at the SAME module-purity slot as the docker gate (top of cli.tsx, before heavy imports), gated by `decideCgroupWrap` (skips container/help/status/prune/wrapped/HUU_NO_CGROUP) and a definitive probe (`systemd-run --user --scope -- true`, ~tens of ms — existence of the binary is NOT enough, the user session bus is the real dependency); re-exec command = `process.execPath + process.execArgv + argv.slice(1)` so tsx dev loaders survive; the PROBE must carry the FULL -p property set (old systemd errors on unknown MemorySwapMax — a bare probe passes while the real wrap dies), the wrapper must FORWARD SIGINT/SIGTERM/SIGHUP to the child (kill <pid> otherwise orphans the scoped app) and map exit signals faithfully (128+N via os.constants.signals — the kernel OOM this feature creates is SIGKILL/137, not 143). docker --memory needs a `docker info {{.MemoryLimit}}` probe (rootless without memory delegation REJECTS the flags — degrade to unlimited, never block). (4) SIZE THE SCOPE BY THE OS RESERVE, NOT THE DIAL: `MemoryHigh = total − reserve`, `MemoryMax = total − reserve/2`. Sizing by the dial double-dials — the sampler is cgroup-aware, so inside the scope `ramTotalBytes` BECOMES memory.max and the internal budget would compute dial% × dial-sized-total (50% dial → 30% effective). Reserve-sized scope = host-safety line fixed at boot; the dial stays the live-tunable utilization target within it. All `HUU_RAM_PERCENT`/`HUU_GUARD_*`/reserve/cap knobs are now in the docker env passthrough Set (a host `HUU_RAM_PERCENT` was silently ignored in-container before).

- [2026-08-04][source:user][task:jcode-bundle-mount][probation] A HOST TOOL THE IMAGE CANNOT FETCH gets bind-mounted, not baked. No public distribution URL for `jcode` exists anywhere in this repo (the setup guide's download line is a literal `https://.../` placeholder), so the image cannot `curl` it and the `INCLUDE_SURF`/`INCLUDE_PENTEST_TOOLS` ARG pattern does not apply. User decision (2026-08-04): mount the host install READ-ONLY at `/opt/jcode` (`lib/jcode-bundle.ts` → `buildDockerArgv` `readonlyMounts`), +0 MB to the image and always the same version the host self-updates to. WHAT THE BUNDLE ACTUALLY IS (measured, jcode 0.67.1): `~/.local/bin/jcode` → symlink → `~/.jcode/builds/stable/jcode` → symlink → `~/.jcode/builds/versions/<v>/jcode`, and THAT file is a 505-byte `/bin/sh` WRAPPER that exports `LD_LIBRARY_PATH=<its own dir>` and execs `jcode-linux-x86_64.bin` (155 MB ELF x86-64, dynamically linked against nothing exotic — libc/libm/libpthread/libdl/librt/libutil/libgcc_s, all present in node:20-slim). So the mount unit is the DIRECTORY holding both files; mounting the launcher alone gives a wrapper whose payload is missing. TIMING CONSTRAINT that shapes the design: the re-exec gate runs at the top of `cli.tsx`, BEFORE any UI, but the backend can be picked LATER in the web UI — so the mount cannot be conditioned on "this run uses jcode". It is OPPORTUNISTIC: mount whenever the host has a usable bundle, and NEVER fail startup when it does not (a host without jcode must still run pi/azure runs). Guards: host must be Linux and the binary's arch must match the container's, else a macOS Mach-O would be mounted into a Linux container. `Dockerfile` does `ln -s /opt/jcode/jcode /usr/local/bin/jcode` rather than `ENV PATH=/opt/jcode:$PATH` — deliberately, so an arbitrary host directory can never SHADOW the container's own `git`/`node`/`sh`; with no bundle mounted the link simply dangles and ENOENT becomes an actionable message. Note `~/.huu` is mounted RW (`extraMounts`, rendered `-v path:path`), which is what lets jcode write under `JCODE_HOME=~/.huu/jcode-home`; a read-only `~/.huu` makes jcode die with `Error: Read-only file system (os error 30)`.
- [2026-09-05][source:user][task:dockerfile-buildkit-portability][probation] **`buildx` era um pré-requisito NÃO DOCUMENTADO e o produto inteiro morria sem ele.** `Dockerfile:25` e `:55` usavam `RUN --mount=type=cache,target=/root/.npm` desde o commit `26d093b` (v1.0.0), sintaxe que SÓ o frontend BuildKit entende. Numa máquina com Docker 29.7.2 e SEM o plugin buildx, todo `npm start` morria em `Step 4/40` com `the --mount option requires BuildKit` — e como huu é docker-only (só `HUU_DEV_NATIVE=1` escapa do re-exec), um plugin de CLI ausente não degradava uma feature, impedia o produto de subir. Três fatos que não são óbvios: (1) **`DOCKER_BUILDKIT=1` NÃO resolve** — sem o plugin ele falha com `BuildKit is enabled but the buildx component is missing or broken`; buildx é um pacote separado (`docker-buildx` no Arch, `docker-buildx-plugin` no Debian), e o README só prometia Node ≥ 20, git e Docker. (2) **O custo de remover os cache mounts é quase zero**: o da linha 55 embrulhava `npm prune --omit=dev`, que não baixa nada, e o da linha 25 só paga quando o `package-lock.json` MUDA — com o lockfile intacto o cache de CAMADA já pula o step inteiro. Os 40 steps constroem no builder legado (imagem de 527MB, os cinco binários do surf presentes). (3) **A CI não pegaria isso nem construindo a imagem**: runners do GitHub têm buildx, então um `docker build` verde lá é falso conforto exatamente para este bug — por isso o guarda (`scripts/check-dockerfile.ts`, 10º passo do gate) é ESTÁTICO. O `# syntax=docker/dockerfile:1.7` da linha 1 também saiu: o builder legado o ignora (não é erro), mas ele anuncia um frontend que o arquivo não usa, e é esse anúncio que convida `RUN --mount` de volta. Efeito colateral bom para o fluxo multi-arch desta mesma skill: sem a diretiva, o BuildKit usa o frontend embutido e deixa de puxar a imagem `docker/dockerfile:1.7` do registry — um pull a menos no caminho que já falhava com TLS-handshake-timeout.
