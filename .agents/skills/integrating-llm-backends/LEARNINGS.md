- [2026-06-30][source:inference][task:deep-research-multirun-oom-pause][probation] pi-coding-agent (v0.73) HAS native session persistence/resume that huu does NOT use — the lever for "pause the agent instead of killing it" under memory pressure. The factory (`backends/pi/factory.ts`) uses `SessionManager.inMemory()` (disposable per task, transcript only in heap), but the SDK also exposes `SessionManager.create(cwd, sessionDir)` which PERSISTS the transcript to disk on every `message_end` (versioned session format `CURRENT_SESSION_VERSION = 3`: `SessionHeader` + JSONL entries), `switchSession` ("used for resume and branching"), a `--resume` CLI flag, and `AgentState.messages` + `serializeConversation()` for serialization. KEY CONSTRAINT confirmed against `docs/pi-coding-agent.md` §1 + factory: agents run IN-PROCESS (every pi session shares huu's single Node heap; isolation is git/fs/ports, NOT an OS process), so there is NO per-PID kill / SIGSTOP / per-agent cgroup, and suspending only the async loop does NOT free RAM. "Pause without losing work" is therefore achievable only via COOPERATIVE CHECKPOINT: abort at a turn boundary (between `message_end`s) → persist session → `dispose()` (frees heap) → later recreate the session from its file + the SAME worktree and continue. That would let the memory-guard PRESERVE work (suspend) instead of kill+requeue-from-scratch (which today loses BOTH the LLM context and the partial worktree). Resume re-pays INPUT tokens (mitigable by prompt caching) but does not re-derive or re-run applied tools. Per-agent footprint measurement (`/proc/<pid>`, cgroup `memory.current`) likewise presupposes making agents subprocesses. Written up as research block G in `~/Downloads/huu-deep-research-escalabilidade-multirun.md` (a deep-research PROMPT, not a repo doc).
